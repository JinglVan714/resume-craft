# 简历制作方法论

> 本文件是简历内容生成的核心指导。聚焦面试官真实视角和实操方法论。

---

## 一、面试官怎么看简历

> 以下来自校招面试官的真实分享（已脱敏）。

**筛选简历时的行为**：
- "筛简历时不仅看实习和学历，还会搜索一些个人特色的关键词。比如有的面试官会搜'游戏经历'，看谁写了自己的游戏成就和玩法思考。"
- "简历太多的时候，先看学校和实习，再看项目。项目描述太长的直接跳过。"
- "技术岗最看重的是项目经历，不是技能清单。列了一堆技术但没有项目佐证的，等于没写。"

**什么简历会被跳过**：
- 信息堆砌没有重点（扫一眼不知道核心竞争力）
- 描述空洞只写"负责了XX"没有具体贡献
- 一份简历走天下没有针对岗位调整
- 技术栈列了 20+ 项无法快速抓住重点

**什么简历会留下**：
- 30 秒内能抓住：你是谁、做过什么、效果怎么样
- 项目经历有 STAR 结构有量化成果
- 有个人特色（开源项目、技术博客、竞赛成绩）

---

## 二、STAR 引导对话

引导用户描述项目经历时，用这四个问题（不要一次性全问，逐个问）：

```
先别急着写，回答我四个问题——
1. 当时面对什么问题或挑战？（这就是 S）
2. 你在里面负责什么？（这就是 T）
3. 你具体做了什么？关键动作是什么？（这就是 A）
4. 最后效果怎么样？有没有数据可以量化？（这就是 R）
```

**STAR 示例**：

差的描述：
```
负责后端开发，使用 Python 和 FastAPI。
```

好的描述（STAR）：
```
在电商平台重构项目中（S），我负责订单系统的后端重构（T）。
采用 Python + FastAPI 重构原有 PHP 服务，引入 Redis 缓存和消息队列（A）。
重构后接口响应时间从 800ms 降至 120ms，系统 QPS 从 500 提升至 2000（R）。
```

## 三、量化成果引导

当用户说"没有数据"时，引导：

- 使用相对值：提升了约 30%
- 使用范围：处理了万级数据
- 使用对比：比原来快了 3 倍
- 使用时间：从原来的一周缩短到两天
- **底线**：没有数据就说"没有精确数据"，不要编造

## 四、表达优化参考

| 原始表达 | 优化方向 | 原因 |
|---------|---------|------|
| "参与了XX项目" | 明确你的具体职责和成果 | 缺少具体贡献和量化结果 |
| "熟悉XX技术" | 补充使用场景和实际案例 | 缺少场景佐证 |
| "沟通能力强" | 用具体协作事例证明 | 空洞声称不如事实佐证 |
| "负责XX开发" | 补充解决的问题和效果指标 | 缺少背景和成果 |
| "使用Python开发" | 说明用 Python 做了什么、效果如何 | 过于泛化 |
| "学习能力强" | 用具体学习经历佐证（如"一周内掌握了XX"） | 空洞声称 |

---

## 五、技术栈分层

引导用户按以下标准分层（不要自己编造，基于用户的项目经历判断）：

| 层级 | 标准 | 示例写法 |
|------|------|---------|
| 精通 | 日常主力，能独立解决复杂问题 | 精通 Python，有 3 年后端开发经验 |
| 熟练 | 用过多个项目，能独立使用 | 熟练使用 Redis 做缓存和消息队列 |
| 了解 | 学过或用过一两次 | 了解 Docker 容器化部署 |

**避免**：
- 过于泛化："熟悉编程"（没有具体技术）
- 过于细节："使用 Python 3.10.2"（版本号无意义）
- 虚假精通：只用过一次就说"精通"
- 技能与项目不匹配：声称精通但项目中没用到

## 六、深挖个人亮点

> 来自面试官："筛选简历时不仅看实习和学历，还会搜索一些个人特色的关键词。"

**什么是个人亮点**：
- 开源项目贡献（GitHub PR、issue）
- 技术博客（持续输出、深度文章）
- 竞赛成绩（ACM、数学建模、黑客马拉松）
- 独立项目（自己做的 side project）
- 特殊经历（跨学科背景、海外交流）

**为什么重要**：面试官在成百上千份简历中找"不一样"的那个人。

---

## 七、禁止事项

- 不编造工作经历或项目
- 不夸大成果数据
- 不虚构证书或技能等级
- 不堆砌无关信息
- 不帮用户把"参与"写成"主导"（除非真源支持）
- 不编造没有精确数据的量化成果
