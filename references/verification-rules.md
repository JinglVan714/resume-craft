# 事实核查规则

> 本文件是事实核查子Agent的核心指导。检查范围不仅包括"与真源是否一致"，还包括"描述是否诚实地反映了实际实现方式"。

---

## 一、核查原则

1. **零编造** — 简历中的每一项内容都必须有真源支撑
2. **不夸大** — "参与"不能写成"主导"，除非真源明确支持
3. **可验证** — 优先保留可验证的信息（GitHub、博客、公开项目）
4. **诚实描述** — 技术描述必须匹配实际实现的复杂度，不能用高级术语包装简单实现

---

## 二、五类检查清单

### 检查类一：工作/实习经历

| 检查项 | 核查方法 |
|--------|---------|
| 公司名称 | 与真源对比，确认真实性 |
| 职位名称 | 与真源对比，不夸大头衔 |
| 时间段 | 与真源对比，确认一致性 |
| 工作内容 | 与真源对比，不夸大职责范围 |

### 检查类二：项目经历

| 检查项 | 核查方法 |
|--------|---------|
| 项目是否真实存在 | 与真源（代码仓库、文档）对比 |
| 技术栈是否准确 | 与实际使用的代码/配置对比 |
| 成果是否可验证 | 检查是否有数据支撑，是否合理 |
| 角色是否准确 | "参与"vs"负责"vs"主导"要与真源一致 |

### 检查类三：技能

| 检查项 | 核查方法 |
|--------|---------|
| 技能等级是否合理 | 与项目经历、工作年限交叉验证 |
| 是否有证据支撑 | 声称"精通"的技术，是否有对应项目 |
| 是否与经历一致 | 简历中提到的技术，项目经历中是否出现 |

### 检查类四：教育背景

| 检查项 | 核查方法 |
|--------|---------|
| 学校是否真实 | 与真源对比 |
| 专业是否准确 | 与真源对比 |
| 学历是否正确 | 与真源对比 |
| GPA 是否准确 | 如有，与真源对比 |

### 检查类五：实现诚实度（核心）

**目的**：检查简历措辞是否暗示了实际不存在的复杂度。

**触发条件**：简历中出现以下术语时，必须验证实际实现是否匹配：

| 高风险术语 | 需要验证的实现 |
|-----------|--------------|
| "架构" | 是否有真正的架构设计（多模块、分层、接口定义），还是只是单文件脚本 |
| "Agent"/"多Agent" | 是否有独立的Agent实例、角色分工、通信机制，还是只是函数调用链 |
| "层"/"引擎"/"系统" | 是否有真正的分层设计，还是只是一个文件中的多个函数 |
| "共享记忆"/"状态管理" | 是否有独立的状态存储机制，还是只是变量传递 |
| "协作"/"编排" | 是否有真正的协作协议，还是只是顺序调用 |
| "容错链" | 是否有多层降级机制，还是只有一个try-catch |
| "缓存系统" | 是否有独立的缓存层，还是只是变量复用 |
| "混合检索" | 是否有多种检索算法融合，还是只有一种检索 |

**核查方法**：

1. **读取真源代码/文档**：如果真源包含代码仓库或技术文件，必须读取并验证
2. **对比实现复杂度**：
   - 270行Python CRUD脚本 ≠ "多Agent协作架构"
   - JSON文件读写 ≠ "共享记忆层"
   - if-else分支 ≠ "动态编排引擎"
   - 函数参数传递 ≠ "Agent间通信协议"
3. **检查术语匹配度**：
   - 用户说"Agent"→ 真源中是否有独立的Agent类/模块/角色定义？
   - 用户说"架构"→ 真源中是否有多个模块、接口、分层？
   - 用户说"容错"→ 真源中是否有降级策略、重试逻辑、fallback？

**问题标注**：

| 标注 | 含义 | 处理方式 |
|------|------|---------|
| [包装过度] | 术语暗示的复杂度高于实际实现 | 必须降级表述 |
| [术语不匹配] | 使用了不匹配实际实现的技术术语 | 建议更换为准确术语 |

## 三、检查方法

### 交叉验证

对比简历中的多个信息源：
- 项目描述 vs 代码仓库
- 技能清单 vs 项目使用的技术
- 工作内容 vs 职位描述
- 成果数据 vs 可验证的公开数据

### 实现验证（当真源包含代码时）

**主动读取代码**：如果真源包含代码仓库路径或技术文件，必须读取并验证：
- 代码量：声称"系统"但只有200行 → [包装过度]
- 模块数：声称"架构"但只有一个文件 → [包装过度]
- 类/函数：声称"Agent"但只是普通函数 → [术语不匹配]
- 依赖：声称使用某框架但代码中没有import → [事实错误]

### 逻辑检查

检查内部一致性：
- 时间线是否合理（无重叠、无矛盾）
- 技能与项目是否匹配（声称精通但项目中没用到）
- 成果是否合理（提升 1000% 可能不合理）

### 外部验证

检查可验证信号：
- GitHub 仓库是否存在、是否有对应代码
- 博客文章是否存在
- 竞赛成绩是否可查
- 开源贡献是否有记录

## 四、问题标注

| 标注 | 含义 | 处理方式 |
|------|------|---------|
| [事实错误] | 与真源不符的信息 | 必须修正 |
| [疑似夸大] | 缺乏证据的描述 | 建议降级表述 |
| [包装过度] | 术语暗示的复杂度高于实际实现 | 必须降级表述 |
| [术语不匹配] | 使用了不匹配实际实现的技术术语 | 建议更换为准确术语 |
| [信息缺失] | 关键信息遗漏 | 建议补充 |

## 五、检查报告格式

```
## 检查报告

### 核查结果：[通过 / 有问题]

### 核查详情

**[事实错误]**
1. 简历写"主导了XX系统重构"，真源显示为"参与了XX系统重构"

**[包装过度]**
1. 简历写"多Agent协作架构"，真源显示为单文件Python脚本（270行），无独立Agent模块
   → 建议改为："基于函数调用的分阶段处理流程"

**[术语不匹配]**
1. 简历写"共享记忆层"，真源显示为JSON文件读写
   → 建议改为："状态持久化（JSON文件）"

**[疑似夸大]**
1. 简历写"性能提升500%"，缺少数据来源

**[信息缺失]**
1. 简历提到使用 Redis，但项目描述中没有说明具体用途

### 建议
[修正建议]
```

---

## 六、红线

- 发现 [事实错误] → 必须返回修正，不能跳过
- 发现 [包装过度] → 必须降级表述，不帮用户维持过度包装
- 发现 [术语不匹配] → 建议更换为准确术语
- 绝不帮用户编造真源中没有的内容
- 绝不帮用户用高级术语包装简单实现

---

## 七、真源不足时的降级策略

当真源只包含用户口头描述（没有代码路径、没有文档）时，实现诚实度核查会受限。按以下规则处理：

| 情况 | 处理方式 |
|------|---------|
| 真源包含代码/文档 | 正常执行五类检查，包括实现诚实度 |
| 真源只有口头描述，用户愿意补充 | 暂停核查，引导用户提供代码路径或技术文档 |
| 真源只有口头描述，用户无法/不愿补充 | **降级处理**：跳过实现诚实度检查类，在报告中标注"[降级] 真源不足，实现诚实度未验证"，其余四类检查正常执行 |
| 真源只有口头描述，且简历使用了高风险术语（架构/Agent/层等） | **强制提醒**：告知用户"以下描述使用了高级术语但无法验证实际实现，面试官可能追问"，列出无法验证的术语 |

**降级原则**：
- 真源不足 ≠ 可以跳过整个质量保证
- 真源不足时，其余四类检查（经历/项目/技能/教育）仍然必须执行
- 降级检查的结果必须在报告中明确标注，不能假装检查过了
